# 에이전트 산출물 보관 (비공개 버킷)

## 왜 따로 두는가

`files` 버킷은 공개다. 채팅 첨부·본문 이미지·폴더 원본이 모두 그 공개 주소를 그대로 쓰고
있어서 지금 와서 닫을 수 없다. 그런데 에이전트가 만드는 것은 계약서 검토 결과나 사내
보고서다 — 주소만 알면 누구나, 언제까지나 열리는 자리에 둘 것이 아니다.

그래서 산출물만 따로 비공개 버킷에 넣고, 볼 때마다 만료되는 서명 주소를 발급한다. 공개
버킷을 통째로 닫는 것보다 옮길 것이 적고, 되돌릴 때도 `app/storage/artifact_bucket.py`
하나만 보면 된다.

## 운영 준비 (한 번)

Supabase 에 **공개 정책이 없는** 버킷을 하나 만든다.

```sql
insert into storage.buckets (id, name, public)
values ('artifacts', 'artifacts', false)
on conflict (id) do update set public = false;
```

서비스 키로만 읽고 쓰므로 RLS 정책은 따로 두지 않는다. 정책을 열어 두면 비공개로 둔 뜻이
없어진다.

## 어느 버킷인지 어떻게 아는가

객체 키가 말한다. 산출물의 키는 `artifacts/` 로 시작한다(`ARTIFACT_PREFIX`).

키를 저장하는 자리(`knowledge_files.source_ref`)가 이미 여럿이라, 버킷을 따로 들고 다니게
하면 그 자리마다 컬럼을 늘려야 한다. 접두사 하나면 `bucket_for(key)` 로 끝난다 — 옛 산출물은
아직 공개 버킷에 있고, 그것도 같은 함수가 가려낸다.

## 설정

| 환경변수 | 기본값 | 뜻 |
| --- | --- | --- |
| `ARTIFACT_BUCKET` | `artifacts` | 산출물 전용 비공개 버킷 이름 |
| `ARTIFACT_URL_TTL_SECONDS` | `3600` | 서명 주소의 수명(초) |

한 시간은 한 번의 대화에서 보고 받기에 넉넉하고, 주소가 새어 나가도 오래 살지 않을 만큼
짧다.

## 주소가 죽으면

파일은 그대로 있다. 화면은 레코드에 함께 실린 `file_id` 로 새 주소를 받아 간다.

```
GET /artifact-url?tenant_id=<조직>&file_id=<객체 키>
→ {"file_id": "...", "file_url": "https://...", "url_expires_at": "..."}
```

**다른 조직의 산출물은 내주지 않는다.** 객체 키를 알아도 그 키가 이 조직의 것으로
`knowledge_files` 에 등록돼 있지 않으면 발급하지 않는다 — 키는 우연히도, 실수로도 새어 나갈
수 있다. 그래서 `/save-to-storage` 는 산출물을 올리자마자(파싱·색인보다 **먼저**) 등록한다.
등록이 파싱 뒤에 있던 때는, 본문을 못 뽑은 파일이 등록 없이 지나가 다음 날 다시 발급받을 수
없었다.
