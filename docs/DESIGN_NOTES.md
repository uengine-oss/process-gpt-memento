# 설계 근거

결정에 이른 실측·버린 대안. 계약(무엇을 하는가)은 [`specs/`](specs/)에 있다.
코드 주석은 한 줄 "왜"와 이 문서의 앵커만 남긴다. 항목 제목이 앵커다.

## 지도

지식베이스의 소비처는 codex 다. codex 는 파일을 직접 읽고 `rg` 로 뒤질 수 있는 에이전트라,
서버가 top-k 청크를 골라 주는 것보다 **어디에 무엇이 있고 무엇부터 읽어야 하는지** 를 주는
쪽이 낫다. 채팅방 폴더 업로드는 파일 더미고, 지식베이스는 미리 만들어 둔 지도다.

밖에서도 같은 방향이다. Claude Code 는 2025-05 에 임베딩·벡터DB·청킹을 걷어내고 grep 으로
바꿨다. Corpus2Skill(*Don't Retrieve, Navigate*, arXiv 2604.14572)은 코퍼스를 계층
디렉터리로 컴파일해 내려가는 방식이 dense retrieval 대비 Token F1 +29% 를 보였다. 우리는
사업별 실제 폴더가 있어 그 논문이 K-Means 로 지어내는 계층을 이미 갖고 있다.

## 카드의 변별력

문서 카드는 "무엇에 대한 문서인가"가 아니라 "이 문서를 열어야 하는가"를 답해야 한다.
동일 골격의 사업 문서가 여러 벌이면 문서 하나만 보고 쓴 요약은 "○○사업 제안요청서"로
수렴한다(Corpus2Skill 도 "cluster summaries collapse onto near-duplicate labels" 로 졌다).
그래서 같은 폴더의 다른 문서 제목을 보여 주고 `distinguishers` 를 쓰게 한다.

## 검색 힌트

grep 은 어휘가 어긋나면 0 을 돌려준다. 한국어는 조사가 붙고 띄어쓰기가 흔들려 더 심하다
(`계약금액` 으로 `계약 금액은` 을 못 찾는다). 그래서 벡터 검색을 힌트로 남겼다. 서버 측 쿼리
확장(HyDE·multi-query·RAG fusion)은 제거했다 — 질문을 고쳐 가며 다시 찾는 일은 에이전트 루프가 한다.

## 흐르는 문서의 쪽 번호

DOCX·HWPX는 파일에 쪽 나눔이 없다. 쪽은 여는 프로그램이 글꼴·용지로 계산한다.

렌더러로 쪽을 계산해 파서 블록에 붙이는 방법을 시험했다(2026-09-23, 샘플 2건). 블록은
전부 쪽에 붙었지만 쪽 수가 틀렸다: HWPX 는 rhwp 46쪽 / 한글 72쪽, DOCX 는 LibreOffice
21쪽 / Word 23쪽. 틀린 쪽 번호는 출처가 없는 것보다 나쁘다.

파일에 남는 흔적도 믿을 수 없다. 로컬 DOCX 40건 중 `lastRenderedPageBreak` 가 있는 것은
14건이고, `docProps/app.xml` 의 `Pages` 는 강제 쪽 나눔이 12개인 문서에도 1 이었다.

업계도 쪽을 약속하지 않는다. Azure Document Intelligence 는 DOCX 한 "페이지"를 3,000자로
정의하고, Copilot·NotebookLM 은 인용을 누르면 구절로 이동한다. Claude Citations 는 PDF만
쪽, 텍스트는 글자 범위다.

결론: 흐르는 문서의 출처는 **구조상 위치 + 원문 발췌**로 한다. 쪽 번호는 PDF·PPTX만.

보여 주는 것은 다르다. 인용을 누르면 원본처럼 생긴 화면을 원해서, 흐르는 문서도 변환본 PDF를 그려 그 위에
블록 자리를 칠한다(2026-09-28, 법령 hwpx 5·docx 5건: 블록 배치 99.6~100%, 칠한 자리의 글자가 블록과 90% 이상
같은 비율 97.5~99.7%). 이때 쪽 번호는 "변환본 기준"으로만 표시하고 앵커로 쓰지 않는다.

여는 시간(2026-09-29, 같은 15건, 로컬): 변환본이 캐시에 있으면 `/document/blocks`·첫 쪽 이미지가 각각 0.02~0.13초.
없을 때 변환은 HWPX(rhwp) 29~69초, DOCX(LibreOffice) 2~10초, 블록 정렬 0.1~0.8초다. 채팅 벤치 두 개가 같이
돌던 중에 잰 값이라 단독이면 더 짧을 수 있다. 인제스트 직후 미리 변환하는 이유이고, 이미 올라와 있던 KB는
첫 열람이 이 시간을 기다린다. 원자료: `test-field/출처테스트/citation-bench-2026-09-29/viewer_timing.json`.

`/document/locate` 는 발췌의 `...`·`…` 을 조각 사이 400자 이내로 이어 찾는다. 모델이 긴 조문을 줄여 옮기면
통째로는 원문에 없어서, 이전에는 인용 범위 전체를 칠했다.

비교는 글자·숫자만 한다(변환본 정렬과 같은 기준). 공백·문장부호·PDF 추출이 남긴 제어 문자(`` 등)·마크다운 기호는
모델이 옮기며 바꾸거나 빼기 쉽고, 표 셀 안 `<br>` 같은 태그는 글자째 먼저 지운다. 정확히 맞는 곳이 없을 때만 낱말 사이
40자 끼어듦을 허용하고 `loose: true` 를 단다(다단 PDF 는 옆 단 낱말이 문장 사이에 끼어 추출되고, 모델은 표의 떨어진 칸을
이어 붙여 옮긴다). 2026-09-29 일반 문서 벤치(Allganize 32문항 × 2벌)에서 codex 인용 게이트가 "원문에 없다"며 부른 발췌
18개를 원문과 대조하니 15개는 발췌가 맞는 자리였다(제어 문자·태그·문장부호 11, 다단 끼어듦·표 칸 잇기 4). 이 기준에서
남는 3개는 모두 원문을 바꿔 쓴 경우다. 법령 벤치 다섯 벌은 이 기준으로 다시 채점해도 엉뚱한 자리가 0이다.
원자료: `test-field/출처테스트/citation-bench-2026-09-29/allganize/`.

위 수치는 그 실패 사례를 보며 규칙을 고친 튜닝 데이터다. 튜닝에 안 쓴 검증셋(Allganize 32 + KoPub 24, codex
docs/DESIGN_NOTES.md#떼어-둔-검증셋-2026-09-29)에서는 끼어듦 20·40·80자에 따라 못 찾음이 55·50·48 로 완만했다. 대신
KoPub 2단 PDF 에서 원문 그대로인 발췌 36개가 어떤 설정으로도 찾아지지 않았다 — 파서가 두 단을 한 줄씩 번갈아 추출해
문장이 낱말 중간에서 끊긴다(`[b89] … 회담 개최에` / `[b90] 옆 단 한 줄` / `[b91] 는 동의하면서도 …`). locate 에 규칙을 더해
덮지 않고, 파서의 읽기 순서로 고칠 일이다(고치면 재인덱싱).

## 섹션

흐르는 문서에서 쪽 대신 쓸 탐색 단위로 섹션을 검토했다(2026-09-23).

명시적 헤딩만으로는 부족하다. 로컬 고유 문서 중 내용 있는 헤딩 문단이 2개 이상인 것은
HWPX 3/31(개요 수준), DOCX 29/53(제목 스타일·`outlineLvl`) 이다. 빈 문단·표 안 문단까지
세면 HWPX 는 8/31 로 나오는데, RFI 처럼 제목을 표 셀에 넣은 문서가 섞여 있어서다. 계약서의 "제1조"나 제안서의 "1.1" 은 눈에는 구조지만 스타일 없이 타이핑돼
파일에는 흔적이 없다. 번호 패턴 규칙은 도메인마다 늘어나므로 쓰지 않는다.

헤딩이 없는 3건(RFI HWPX, NDA DOCX, 양식 보고서 DOCX)에 카드용 LLM 으로 섹션 시작
블록을 고르게 했더니 조항·번호 체계·양식 항목으로 나뉘었다. 문서당 LLM 1~2회, 10초 안팎.
섹션은 탐색용이고 인용의 정확성은 블록이 지므로, 섹션이 조금 틀려도 출처는 틀리지 않는다.

## HWPX 인라인 요소 뒤 텍스트

`<hp:t>2.1<hp:tab/>본문…</hp:t>` 에서 `node.text` 만 읽으면 "2.1" 만 남는다. 로컬 고유 HWPX
31건 중 가나 RFI 는 원문 25,839자 중 3,902자만 남았다. 헤딩은 남아서 출력만 보면 멀쩡해
보였다. 수정 후 31건 합계 207,461 / 209,208자. 기존 인덱스는 재인덱싱해야 고쳐진다.

## XLSX 시트 번호

시트 번호를 1-based 로 넣었는데 페이지 저장·청크 경로는 `page` 를 0-based 로 보고 +1 한다.
로컬 XLSX 54건 모두 첫 시트가 2쪽으로 저장돼 있었다. 파서가 0-based 로 넣도록 맞췄다.

`/retrieve-by-indices`, `/preview/pdf-highlight` 도 지웠었다. office-mcp 가 이 셋을 부르고,

## PDF 읽기 순서

PDF 본문은 **PDF 에 기록된 글 순서**(PyMuPDF `get_text("blocks")` 의 기본 순서)를 따른다. 예전에는 블록을
세로 위치로 정렬했는데, 2단 문서에서 두 단의 줄이 번갈아 나왔다(soffice PDF 는 줄마다 블록이라 특히 심하다).

세 방식을 글 블록만으로 비교했다(`test-field/parser-bench/exp_order.py`).

| 방식 | olmOCR multi_column (텍스트 레이어 PDF) | 09-29 게이트가 거부한 발췌 | 합성 2단 soffice / reportlab |
|---|---|---|---|
| 세로 위치 정렬(예전) | 397/841 | 1/25 | 9/26, 20/26 |
| **기록 순서** | **491/841** | **20/25** | 26/26, 26/26 |
| 단 인식(넓은 요소로 구역을 나누고 구역 안을 세로 빈틈으로 가름) | 485/841 | 13/25 | 26/26, 26/26 |

기록 순서와 단 인식은 서로 다른 PDF 에서 이기고(23 대 22개), 기록 순서가 엉망인 PDF 를 가려낼 신호(같은 단에서
위로 크게 뛰는 비율)는 두 무리에서 차이가 없었다. 그래서 섞지 않고 가장 단순한 기록 순서를 쓴다. Word·한글·
LibreOffice·InDesign 류 생성기는 읽는 순서로 글을 적는다.

표는 그 안에 가운데가 들어가는 글 블록 자리에 넣고(가장자리만 걸친 제목·출처 줄은 살린다), 그림 설명은 같은
단(가로로 겹치는)에서 바로 위 블록 뒤에 넣는다(`place_key`). 두 칸 이상에 글이 없는 '표'는 선·글자 도형을
표로 오인한 것이라 버린다.

## 괘선 없는 표

`unruled_tables.py`. 표의 한 행은 같은 높이에 글이 옆으로 늘어서고(블록 하나 안의 줄들, 또는 이어지는 블록들)
본문 문단은 줄이 위아래로 쌓인다. 옆으로 늘어선 행이 3개 이상 이어지고, 칸 수가 같고, 칸의 가로 범위가 겹치고,
칸 사이가 줄 높이 이상 벌어져 있으면 표로 감싼다. 바로 위의 같은 칸 수 행은 머리행으로 붙인다(머리 글은 가운데,
숫자는 오른쪽 정렬이라 칸 위치로는 안 맞는다). 칸 안에서 줄이 바뀌는 행은 표로 보지 않는다(놓치는 쪽을 택함).
글을 지우거나 순서를 바꾸지 않는다 — 바꾸기 전 글자·숫자 수가 같은지 세고 다르면 바꾸지 않는다. `PDF_UNRULED_TABLES=false` 로 끈다.

확인(`test-field/parser-bench/exp_unruled.py`, 규칙에 쓰지 않은 문서 약 3,400쪽): olmOCR table 302 → 335/951, multi_column
486 → 486, headers_footers 그대로. 새로 생긴 표 76개를 원문 조각과 하나씩 대조했다 — 데이터 표, 판결문 머리·연락처 같은
이름표-값 목록, 칸이 넓은 목차, 원래 깨진 텍스트 레이어 2건. 규칙을 켜기 전과 후 글자가 달라진 쪽 0.

칸 틈 조건은 첫 검토에서 한 줄이 조각나 추출된 일본어 본문이 2열 표가 된 것 때문에 넣었다(틈이 줄 높이의
0.75배, 목록·목차 0.66~0.87배, 실제 표 1.17배 이상). 틈이 좁은 진짜 표는 놓친다. 블록 목록(`blocks`)과 줄 좌표(`dict`)는
블록 번호가 다르게 매겨지는 PDF 가 있어 좌표로 짝짓는다 — 번호로 짝지었을 때 문단이 표 행에 흡수돼 글이 사라졌다.

## 선 없는 하위 행

`subrows.py`. 한컴 PDF 통계표는 하위 행(연도·분기, 전월비·동월비, 제조업 아래 출하·내수·수출) 사이에 가로선이 없어
`find_tables` 가 수십 행을 한 칸에 `<br>` 로 담는다. 값은 남지만 행 머리와의 짝이 사라진다. LLM 은 몇 번째 줄인지
세다 틀린 값을 댄다(아래 질의응답의 "틀린 값"). 실제 보도자료 PDF 셀이 53% 만 표로 나오던 원인이 이것이었다.

`find_tables` 가 찾은 표 안에서만, 한 행의 글자를 줄 높이로 다시 나눈다. 글자는 감싸는 가장 작은 칸의 행에
배정한다(병합 칸·자잘한 행이 겹쳐도 한 글자는 한 행). 칸은 보이는 간격으로 끊은 토큰의 가운데로 정한다(이름과 값
사이에 공백 문자가 없는 PDF 가 있다). 나누는 조건과 이름 붙이기:

- 숫자가 둘 이상인 줄이 두 줄 이상이어야 하위 행이다. 머리 칸의 줄바꿈(확정치/(A))은 그대로 둔다.
- 값 아래 (비율)·(0.8배)를 쌓은 칸은 한 값이다. 괄호는 위 줄 값 밑에만, 다른 글은 위 줄 빈칸에만 있으면(두 줄
  가운데 찍힌 연령·인원 포함) 위 줄에 "값 (비율)" 로 붙인다. 위 줄 이름 밑에 제 이름이 있으면(총투자/증감률) 제 행.
- 값 없는 이름 줄이 값 줄만큼 있으면 나누지 않는다(줄바꿈된 이름 칸). 칸 한 줄이 40자를 넘는 행(쪽 테두리를
  표로 잡아 문단이 든 행)도 나누지 않는다.
- 이름 열(1/4·전월비처럼 숫자 아닌 이름이 값 줄 절반 이상에 있는 열과 그 왼쪽)의 빈칸은 위 값을 잇는다(연도).
- 값 없는 이름 줄은 이어진 것끼리 한 이름(담배제품/현재/사용률)으로 묶어 세로로 가장 가까운 값 줄에 붙인다.
  두 값 줄 가운데 찍힌 이름(백화점 → 전월비·동월비)은 반 줄, 위 행 이름은 한 줄 떨어져 있어 갈린다. 값 줄마다 제
  이름이 있으면 바로 옆 값 줄에만 묶음 이름을 앞에 붙인다(항공 → 국내·국제). 세로쓰기 한 글자 이름(생/산)은 합친다.
- 위첨자 각주 표시(`*`)는 아래 줄 값에 붙인다.
- **나눈 결과가 반듯한 격자일 때만 쓴다.** 값 줄마다 값 칸 수가 비슷하고(최대의 60% 이상), 한 칸에 숫자 하나
  ("값 (비율)", "2024. 8" 은 하나), 쉼표 묶음이 세 자리여야 한다(좁은 칸 이웃 숫자가 붙으면 깨진다). 아니면 그 행은
  원래대로(`<br>` 묶음) 둔다 — 틀린 격자는 LLM 이 자신 있게 틀린 값을 대게 한다.

`PDF_SPLIT_SUBROWS=false` 로 끈다.

확인(`test-field/parser-bench`, 끔 → 켬, 같은 날 같은 코드에서 이 설정만 바꿈):

| 열 머리 / 행 머리 | 21% / 37% | 37% / 75% |

질의응답에서 같은 문항에 쪽 글자 전체(표 구조 없음)를 주면 79%, Camelot lattice 80%, img2table 68~74%,
Camelot stream 68% 였다. 같은 문항을 다시 물으면 조건마다 ±2%p 흔들린다. 문항은 정답 표로도 틀리는 것을 뺐다.

글 보존: 실제·KoPub·Allganize·olmOCR 4,977쪽에서 원래 결과의 낱말이 새 결과 같은 쪽에서 안 보이는 쪽 1(각주 표시
"1)" 이 옆 이름에 붙었다). 바뀐 표는 실제 168 / KoPub 28 / Allganize 10 / olmOCR 6
(`test-field/parser-bench/subrows_review`, 원문 표 조각 | 끔 | 켬). 육안 대조: grdp 분기표, 산업활동 주요 지표·소매업태·
제조업 재고·설비투자, 국민건강영양조사 연령별 지표, 해외직접투자, 추석 교통수단, 국가재정 성장률, 유라시아 교역,
olmOCR 날씨표. 나누지 않아야 할 표(건설 계약액·국고채 값/(비중), 안건 목록, 쪽 테두리 표)는 그대로인지 확인했다.
규칙을 만들 때 쓰지 않은 KoPub 유아교육 보고서처럼 원래 결과부터 행 전체가 한 칸에 뭉친 표는 격자 관문에 걸려
대부분 그대로 남는다.

다른 추출기를 쓰지 않은 이유(CPU 도구만, 같은 병합 채우기 후 채점): Camelot lattice 는 선 기준이라 같은 칸 뭉침이
그대로다(행 머리 38%). Camelot stream·img2table 은 셀 93·92% 를 내지만 쪽 전체를 글자 정렬로 보는 stream 은 본문
문서 231개 중 202개에 표를 만들고, img2table 은 OpenCV 의존에 이름 칸 글이 섞인다. 둘 다 행 머리 67~68%.

남은 것: 표 영역이 이름 열을 빼고 잡힌 표(산업활동 제조업 재고 표의 "1차 금속" 등은 원래부터 표 밖),
`find_tables` 가 칸을 잘못 잡은 표(상수도 요금 표의 "물사용량" 자리에 "구 분") — 나누기 전부터 틀려 있다.
규칙이 여럿이라 새 형태의 표에서 또 어긋날 수 있다. 격자 관문이 마지막 안전판이고, 바뀐 표 검토 화면으로 본다.

## 하지 않은 것

- **개인/공용 공간 분리.** 지도의 값어치는 완결성에서 나오는데 공간을 쪼개면 사람마다
  지도가 달라진다. 필요가 분명해지면 폴더 속성 하나로 시작한다.
- **자료 분류(`doc_role`).** 분류마다 다른 길을 태우면 같은 폴더의 지도가 쪼개진다.
  폴더 카드 키가 분류를 포함하던 때 한 폴더에 분류 수만큼 카드가 생기고 서로 덮어썼다.
- **청킹 전략 변경.** 청크는 힌트와 `/documents/full-text` 에만 쓰인다. 바꾸려면
  `benchmark/` 로 수치를 먼저 낸다.
