# 벡터 DB 전환 (Chroma → Qdrant) 검토 보고

## 1. 요약

폐쇄망 지식베이스의 임베딩 인덱스가 50GB를 넘기면서 Chroma의 메모리 점유가 운영 한계에
도달했다. 동일 조건 벤치마크 결과, Qdrant 전환 시 **실질 RAM 점유가 4.4배 줄고(77% 절감),
실서비스 경로(테넌트 필터 검색)의 지연이 규모에 비례해 증가하는 문제가 해소**된다.

| 지표 (500만 벡터 환산) | Chroma | Qdrant | 개선 |
|---|---:|---:|---|
| 실질 RAM 점유 (회수 불가) | 37.1 GB | 8.5 GB | **4.4배 감소** |
| 검색 지연 p50 (테넌트 필터) | 15.5 s | 55 ms | **약 280배** |
| 디스크 사용량 | 32.0 GB | 38.6 GB | 1.2배 증가 |

디스크 20% 증가는 원본 벡터와 int8 양자화본을 함께 보관하는 설계의 대가이며, 이것이
메모리 절감의 실제 원리다.

---

## 2. 측정 방법

- **대상**: Chroma 1.5.9 / Qdrant v1.19.0, 각각 단일 컨테이너
- **데이터**: 1536차원 합성 벡터(실서비스와 동일 차원, L2 정규화하여 실제 임베딩 분포 모사)
- **규모**: 5만 / 15만 / 30만 건 3개 지점
- **측정 시점**: 적재 후 최적화 정착 → 컨테이너 재시작 → 질의 50회 → 측정
  (재시작 없이 재면 적재 버퍼가 섞이고, 정착 대기 없이 재면 최적화 중 상태가 잡힌다)
- **지연**: 미리 생성한 질의 벡터를 직접 투입.
  **임베딩 API 호출은 제외** — 포함하면 500~1000ms의 임베딩 지연이 엔진 차이를 덮는다.
- **메모리**: cgroup 기준 `anon`(익명 메모리, 회수 불가)과 `file`(페이지 캐시, 회수 가능)을 분리.
  두 엔진의 성격이 다르므로 총량 비교는 오해를 만든다.

재현: `python benchmark/bench_chroma_vs_qdrant.py --target 300000 --checkpoints 50000,150000,300000`

---

## 3. 메모리 실측

| 벡터 수 | Chroma anon | Chroma file | Qdrant anon | Qdrant file |
|---:|---:|---:|---:|---:|
| 0 (기준선) | 13 MB | 0 MB | 244 MB | 2 MB |
| 50,000 | 396 MB | 0 MB | 342 MB | 72 MB |
| 150,000 | 1,184 MB | 0 MB | 518 MB | 77 MB |
| 300,000 | 2,295 MB | 0 MB | 766 MB | 83 MB |

**벡터 1건당 한계 메모리** (기준선 제외, 최소제곱 회귀)

- Chroma: **7,950 B/vec** — 1536×4B(=6,144B) 원본 벡터 + HNSW 링크. 전량 힙 상주.
- Qdrant: **1,774 B/vec** — 1536×1B(=1,536B) int8 양자화본 + 관리 구조.

이론 검산과 일치한다(원본 float32 대비 int8은 정확히 1/4). 즉 이 절감은 벤치마크 특성이
아니라 설계에서 예측되는 값이며, 규모가 커져도 유지된다.

주목할 점은 **Qdrant의 `file`이 83MB에서 멈춘다**는 것이다. 원본 벡터와 HNSW 그래프는
디스크에 mmap되어 있고, 질의가 실제로 건드린 페이지만 캐시에 올라온다. 이 영역은 메모리
압박 시 커널이 회수하므로 OOM 요인이 아니다. 반면 Chroma의 `anon` 2,295MB는 회수 대상이
아니다 — **여기가 현재 폐쇄망에서 메모리가 터지는 지점이다.**

## 4. 검색 지연 실측

| 벡터 수 | Chroma 무필터 | Chroma **필터** | Qdrant 무필터 | Qdrant **필터** |
|---:|---:|---:|---:|---:|
| 50,000 | 5.0 ms | 153.3 ms | 30.9 ms | 15.8 ms |
| 150,000 | 5.8 ms | 456.3 ms | 30.8 ms | 16.4 ms |
| 300,000 | 6.6 ms | **928.6 ms** | 31.1 ms | **30.9 ms** |

이번 검토에서 가장 중요한 발견이다.

**Chroma는 필터 없는 검색은 빠르다**(5~7ms, 규모와 무관). HNSW 인덱스가 정상 동작한다.
그런데 **메타데이터 필터를 걸면 규모에 정비례해 느려진다** — 데이터 6배에 지연 6.1배.
Chroma가 필터 조건에 맞는 대상을 먼저 추린 뒤 그 집합을 전수 스캔하기 때문이다(O(n)).

문제는 **memento의 모든 검색이 `tenant_id` 필터를 반드시 포함**한다는 점이다. 즉 실서비스는
항상 느린 쪽 경로만 탄다. 500만 건 환산 시 질의 1건당 **약 15.5초**다.

Qdrant는 payload 인덱스로 필터를 처리하고 HNSW를 그대로 태우므로 데이터 6배에 지연 2.0배에
그친다(sublinear). 500만 건 환산 시 약 55ms.

> 정직하게 덧붙이면, **필터가 없는 검색만 놓고 보면 Chroma(6.6ms)가 Qdrant(31.1ms)보다 빠르다.**
> Qdrant는 디스크의 원본 벡터로 재채점(rescoring)하는 비용을 치르기 때문이다. 다만 실서비스
> 경로가 아니므로 전환 판단에는 영향이 없다.
>
> Qdrant 외삽은 측정점 3개 기반이라 근사치다. 확실한 것은 "규모에 선형 비례하지 않는다"는
> 점이며, Chroma의 선형 증가는 3개 지점이 거의 정확히 비례해 확정적이다.

## 5. 적재 성능

30만 건 적재 기준 Chroma 410초(732 vec/s), Qdrant 414초(725 vec/s)로 **차이 없음**.
적재 속도는 전환 판단 요소가 아니다.

단, 이관 시에는 Qdrant의 HNSW 인덱싱을 일시 중단(`indexing_threshold=0`)한 뒤 적재를
마치고 재개하는 방식을 쓴다. 매 배치마다 그래프를 재구성하지 않아 대량 이관이 빨라진다.

---

## 6. 설계 근거

Qdrant의 이점은 "디스크에 둘 수 있다"가 아니라 **"RAM에 올릴 양을 줄인다"** 쪽이다.
적용한 설정은 다음과 같다.

| 설정 | 값 | 역할 |
|---|---|---|
| `quantization` | int8, `always_ram=true` | 양자화본만 RAM 상주 — 벡터당 1/4 크기 |
| `vectors.on_disk` | true | 원본 float32는 디스크(mmap), 재채점 때만 읽음 |
| `hnsw_config.on_disk` | true | HNSW 그래프도 mmap |
| `on_disk_payload` | true | 메타데이터는 디스크, 필터는 RAM의 payload 인덱스로 |
| `rescore` + `oversampling=2.0` | — | 양자화본으로 후보를 넓게 뽑고 원본으로 재채점 |
| HNSW `m=16`, `ef_construct=100` | — | Chroma와 동일 — 리콜 특성 보존 |

검토 중 발견해 함께 반영한 사항: payload 인덱스에 **실제로 필터에 쓰이지 않는 키**
(`file_name`, `file_path`, `document_row_id`)가 포함돼 있었다. payload 인덱스는 RAM에
상주하고 값이 고유할수록 비싼데, 특히 `document_row_id`는 포인트마다 값이 달라 비용이
가장 컸다. 이를 제거해 15만 건 기준 Qdrant anon이 **790MB → 518MB로 34% 추가 절감**됐다.

## 7. 이관 검증 결과

운영 데이터(837 벡터)로 이관 후 전 구간을 대조했다.

- **무결성**: 837/837 이관. 표본 50건 벡터·메타데이터 대조 — 누락 0, 불일치 0.
- **API 동등성**: 동일 질의 5건에 대해 반환 청크가 **순위까지 100% 일치**.
- **필터 경로**: 단일/다중 `file_id`, `exclude_chunk_ids` 제외, 잘못된 테넌트 → 빈 결과.
  전부 Chroma와 동일.
- **임베딩 조회**: 44건 코사인 유사도 1.00000000.
- **재임베딩 불필요**: 기존 벡터를 그대로 이관 — 임베딩 API 재호출 0회.

## 8. 리스크 및 대응

| 항목 | 내용 | 대응 |
|---|---|---|
| 디스크 20% 증가 | 원본+양자화본 동시 보관 | 500만 건 기준 32→39GB. 용량 확보 |
| 랜덤 I/O 의존 | `on_disk=true`는 탐색 hop마다 랜덤 리드 | **NVMe 확인 완료** — 적정 |
| 버전 정합 | 서버·클라이언트 major/minor 일치 필요 | v1.19.0 ↔ qdrant-client 1.19.x로 고정 |
| 롤백 | 전환 실패 시 복귀 수단 | Chroma 데이터 보존. `VECTOR_BACKEND=chroma`로 즉시 복귀 |

---

## 9. 결론

전환을 권고한다. 근거는 메모리 절감(4.4배)만이 아니라, **현재 폐쇄망에서 체감되는 조회
지연의 원인이 Chroma의 필터 검색 O(n) 특성이며 이는 규모가 커질수록 악화되는 구조적
문제**라는 점이다. 데이터가 늘어날수록 격차는 벌어진다.
